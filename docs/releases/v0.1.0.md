# v0.1.0 — first precompiled image for the Google Hayato

The first release: a Debian arm64 system that boots on the **Google Hayato rev1** (ASUS Chromebook
Detachable / Flip CM3 CM3200 — MediaTek MT8192 "Asurada", `google-asurada`) from a microSD card
with the stock ChromeOS firmware in place. Hardware support is reused from Nura (postmarketOS):
its kernel, device trees, patches, modules and boot flow, with Debian userspace instead of Alpine.

## What is in it

- Debian `forky` (testing), `arm64`, bootstrapped with `debootstrap`.
- Mainline Linux **7.2.7** with Nura's config and patches, built with `make LLVM=1`.
- The boot chain is untouched: depthcharge loads a **signed FIT "kpart"** from the ChromeOS kernel
  partition, exactly as Nura and ChromeOS do. No firmware is written.
- The sway session ported from the maintainer's Nura install (solarized theme, waybar, Alacritty,
  greetd + tuigreet, `keyd`), with every deviation documented in `uis/sway/README.md`.
- Working on hardware: display (Panfrost), keyboard and touchpad, both storage devices, Wi-Fi
  (`rtw88_8822ce`), Bluetooth (`rtl_bt`), audio through the MT8192 UCM boot sequence,
  suspend/resume, the Lock key, the brightness keys, and an NTP-synchronised clock.

## Validation

This is not a "it builds" release. The image is the system a `check-system.sh` report was taken
from **on the device**, and both reports are kept in the repository under `reports/`. The second
one — a card written from a committed tree — is **51 OK, 2 WARN, 0 FAIL**. The two WARNs are the
upstream `sbs-8-000b` fuel-gauge noise and a world regulatory domain, which only means no access
point had provided a country yet.

## Assets

| asset | what it is |
|---|---|
| `google-asurada.img.xz` | 4 GiB disk image: the three ChromeOS GPT partitions (kernel, `/boot`, root), ready for `dd` |
| `google-asurada-rootfs.tar.zst` | the same root filesystem as a tarball (with `/boot` inside), for writing your own card with `scripts/write-sd.sh` |
| `google-asurada.vmlinuz.kpart` | the signed FIT kernel partition of that image; it embeds the image's `root=UUID`, so it belongs to this image and no other |
| `SHA256SUMS` | SHA-256 of the three assets |

```sh
sha256sum -c SHA256SUMS
xz -dc google-asurada.img.xz | sudo dd of=/dev/mmcblk1 bs=4M conv=fsync
```

On the Chromebook: developer mode, `crossystem dev_boot_usb=1 dev_boot_signed_only=0`, insert the
card, press **Ctrl+U**. It comes up silently to a greetd prompt: user `brunux`, password `debian`,
passwordless sudo — change the password before using it for anything real.

## What it does not carry

The artifact is sanitized before it is compressed and the release refuses it while anything is
left (`scripts/lib-dist.sh`), because the build rootfs does carry the maintainer's state:

- **no Wi-Fi profiles** — the maintainer's own builds import his networks, PSKs in clear; the
  released image knows no network and asks you for one;
- **no SSH host keys** — they are generated on first boot (`sshd-keygen.service`), so every
  installation has its own;
- **no `machine-id`** — systemd generates a fresh one on first boot;
- no personal files from the maintainer's home: no notes, no keys, no shell history. What is in
  `/home` is the ported session configuration, which lives in this repository.

## Known limitations

- The image is 4 GiB. A larger card keeps the space after `p3` unused; writing the tarball with
  `scripts/write-sd.sh` instead sizes `p3` to the whole card.
- The tarball's `/etc/fstab` is the unconfigured one the build leaves behind:
  `write-sd.sh` generates the real one, so use it rather than copying files by hand.
- Artifacts are not byte-reproducible yet (FIT timestamp, filesystem UUIDs).
- `scripts/install-emmc.sh` exists but had not been run on the reference machine when this release
  was cut: booting from the card is the supported path here.
- Battery percentage is the capacity reading only. The gauge reports `Unknown chemistry: OTC0` and
  spams the journal on upstream kernels — Nura's own log has the same lines.
